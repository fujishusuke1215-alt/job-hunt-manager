# Job Hunt Manager — Portfolio Description

## A. 30秒説明

Job Hunt Manager は、就職活動で散らばりやすい企業情報、選考状況、締切、評価を一元管理する Web アプリです。メールや採用ページの更新はすぐに正式データへ入れず、Finding として集めて確認・承認する設計にしました。Google Login と RLS により、ユーザーごとのデータを分離しています。

## B. 1〜2分説明

応募候補が増えると、Gmail、採用ページ、MyPage、締切、選考メモ、企業評価がそれぞれ別の場所にあり、確認だけで時間がかかります。そこで、企業・選考・評価を一つの画面にまとめ、更新情報を Finding inbox に集める仕組みを作りました。

収集した情報は誤検出や文脈不足の可能性があるため、自動で確定せず preview / approve / reject を挟みます。承認された情報だけがアプリの正式データになります。React / TypeScript で UI を作り、Supabase Auth と RLS で個人データを分離しました。自分の運用では、Gmail と公開採用ページを定期収集する Owner 専用の自動化も追加しています。

## C. 開発背景

課題は「情報がないこと」ではなく、「必要な情報が複数の場所にあり、確認のたびに探し直すこと」でした。締切や選考の変化を見落とさず、比較や応募の判断に時間を使える状態にするため、収集・確認・確定を分ける構成にしました。

## D. 一般ユーザー向け機能

- Google Login とユーザー単位のデータ管理
- 企業、選考状況、締切、評価、Research Fact の管理
- 今日の要対応、直近7日、更新候補のダッシュボード
- ランキングと評価項目のカスタマイズ
- CSV preview / validation を使った候補企業の初期登録
- Finding の確認、承認、却下
- 架空データのみを使う公開 Demo

## E. 自分専用に追加した機能

- 個人 Gmail の就活関連メールを対象にした Initial Backfill と日次増分収集
- 公開採用ページの GitHub Actions による定期監視
- 個人用 CSV からの候補企業・監視対象の初期登録
- Apps Script と Gmail API を用いた Owner 専用 Collector

これらは一般ユーザー向け Gmail 連携として公開している機能ではありません。通常の Google Login と Gmail の権限は分離しています。

## F. 技術的に工夫した点

### Collector と正式データの分離

メールや Web の収集結果は Finding として保存し、正式データへ直接書き込みません。誤抽出を利用者が確認でき、承認の単位も明確になります。

### 重複と増分処理

Finding には fingerprint を使い、同じ内容を繰り返し通知しにくい構成にしました。Web 側は正規化したページ差分を扱い、Gmail 側はメッセージ ID を基準に重複を防ぎます。初回は backfill、以後は増分処理とし、再実行可能な状態を保持します。

### 監視対象の派生

候補企業を保存すると、監視対象がその情報から派生する設計です。CSV を毎回直接編集するのではなく、通常の企業追加フローを今後の運用の起点にできます。

### 失敗の分離

Web Collector は対象サイトごとに失敗状態を持ち、1社の取得エラーで他社の確認を止めないようにしています。

## G. セキュリティで工夫した点

- Supabase RLS でログインユーザーごとに行を分離
- 公開 Demo と本人データを分離
- OAuth secret、service role、collector token、Gmail token をクライアントやリポジトリに置かない
- 個人用 CSV と MyPage 用 private CSV を Git ignore で保護
- Gmail 本文全文、password、認証コードを正式データに保存しない
- 通常ログインは基本プロフィール情報だけを要求し、Gmail / Drive scope を要求しない

## H. 実装上難しかった点

難しかったのは、自動化の便利さと個人情報の扱いを両立する点でした。すべてを自動確定すると誤抽出が危険になり、すべて手入力にすると確認負荷が下がりません。そこで、Collector、Finding、承認済みデータを分け、個人 Gmail の自動化も通常ログインから独立させました。

## I. 今後の拡張

- 新しく追加した1社だけを対象にした Gmail 履歴確認
- Collector の最終成功時刻と stale warning の画面表示をさらに充実
- 企業ごとの監視ルールを UI から設定
- Finding の分類精度を改善するルール設定

## J. 面接で聞かれそうな質問と回答例

### なぜ自動収集結果をそのまま反映しないのですか？

メールや Web ページは誤検出、重複、文脈不足が起こり得るためです。Finding として提示して確認・承認を挟むことで、効率化と情報の正確さを両立させました。

### なぜ Gmail 連携を一般機能にしていないのですか？

個人メールの扱いは権限、プライバシー、運用責任が大きいためです。通常ログインは最低限の identity scope にとどめ、個人用途の Gmail Collector は所有者専用の別設定として切り分けています。

### データ分離はどう実現していますか？

Supabase Auth のユーザー ID を基準にし、Row Level Security で他ユーザーの行を読めない・更新できないようにしています。公開 Demo も実データとは別の架空データです。

### 一番重視した設計判断は何ですか？

「自動化しても、最終判断は利用者が持つ」ことです。Collector の出力を正式データと分離したことで、情報の取りこぼしを減らしつつ、誤った自動更新を避けています。
